# Multi-Agent Travel Planner: UI 與住宿候補前置流程設計

## 1. 文件目的

本文件定義 Multi-Agent Travel Planner 的新一版前端互動流程，重點是把原本偏晚才出現的地圖與住宿資訊，提前到旅程建立階段。新版目標是讓使用者在正式啟動 itinerary workflow 前，先完成目的地、預算與住宿候補選擇，並以右側地圖即時呈現城市與住宿位置。

本文件只涵蓋以下變更：

- 主畫面改為左表單、右地圖。
- `旅遊天數`、`總預算` 與 `住宿預算` 改為「滑桿 + 數值輸入同步」。
- 住宿不再要求手動輸入名稱，而是根據 `目的地 + 住宿預算(NTD)` 即時推薦 3 個候補。
- 點選住宿候補時，地圖跳轉並高亮該住宿。
- 只有 `目的地` 為必填；其他欄位可空白，表示交由系統推薦或暫時不納入硬性驗證。

本文件不重寫原有多 Agent 驗證與回退流程；它只調整 workflow 的前置輸入與 UI 呈現方式。正式行程驗證、預算 gate、節奏 gate 與 Langfuse trace 仍沿用既有設計。

## 2. 設計目標

新版 UI 必須同時滿足四個要求：

1. 使用者一進頁面就能看見地圖，而不是只在結果頁看到地圖。
2. 住宿選擇要從「手動填飯店名稱」改成「系統推薦候補，使用者點選」。
3. 輸入 `目的地` 後，右側地圖就應跳到該城市，形成即時回饋。
4. `總預算` 與 `住宿預算` 都以 `NTD` 呈現，避免使用者在 UI 第一層直接面對 `JPY`。
5. 所有範圍型欄位必須同時支援滑桿與手動輸入，且共享相同邊界驗證。

## 3. 非目標

以下項目不在這次變更範圍內：

- 不新增 OTA、飯店比價網站或訂房平台的正式價格整合。
- 不宣稱住宿候補一定有精確房價。
- 不把整個 app 改成多步 wizard。
- 不改寫既有 itinerary agent、pace gate、budget gate 的核心驗證邏輯。
- 不讓空白欄位直接等於已驗證資料；空白只代表「尚未指定」或「交由系統推薦」。

## 4. 方案比較

### 4.1 方案 A：左表單 + 右地圖 + 即時住宿候補

流程如下：

1. 左邊維持主要參數表單。
2. 右邊固定顯示地圖。
3. 使用者輸入 `目的地 + 住宿預算(NTD)` 後，系統立即查出 3 個住宿候補。
4. 點選候補時，左側寫入選定住宿，右側地圖跳到該住宿位置。
5. 使用者再按下 `開始規劃`，將已選住宿送入正式 workflow。

優點：

- 符合使用者想要的畫面與互動。
- 地圖從一開始就成為主要工作區，不是結果附件。
- 住宿搜尋是 itinerary workflow 的清楚前置步驟。
- 對現有程式的衝擊集中在 UI 與 TripSpec 建立入口，不必拆掉後端 workflow。

缺點：

- 需要新增住宿候補搜尋與地圖狀態管理。
- 需要處理「候補尚未選定時不能開始規劃」的表單限制。

### 4.2 方案 B：多步驟 wizard

把畫面改成：

1. 選目的地。
2. 選住宿候補。
3. 填偏好與預算。
4. 開始規劃。

優點：

- 流程明確，狀態切分清楚。

缺點：

- 改動太大。
- 展示時會偏流程式表單，不像可即時互動的規劃面板。
- 與現有 single-page Streamlit 架構不一致。

### 4.3 方案 C：保留單欄表單，地圖下放

僅在單欄表單下方補住宿候補與地圖。

優點：

- 實作成本最低。

缺點：

- 不符合使用者指定的左右布局。
- 地圖存在感不足，展示效果弱。

### 4.4 建議方案

採用 **方案 A**。

理由是它完整符合使用者指定的互動方式，同時保留現有 workflow 主體，只調整前置輸入與畫面結構，風險最低、收益最高。

## 5. 畫面結構

主畫面改為兩欄：

- **左欄：旅程表單與住宿候補**
- **右欄：互動地圖**

### 5.1 左欄欄位

| 欄位 | 類型 | 規則 |
| --- | --- | --- |
| 目的地 | 文字輸入 | 必填 |
| 旅遊天數 | 滑桿 + 數值輸入 | 必填；最小 1、最大 10 |
| 總預算 (NTD) | 滑桿 + 數值輸入 | 必填；最小 1,000、最大 300,000 |
| 住宿預算 (NTD) | 滑桿 + 數值輸入 | 必填；最小 0、最大 150,000；只用於住宿候補篩選提示 |
| 興趣 | 文字輸入 | 可空白 |
| 必去景點 | 文字輸入 | 可空白 |
| 必去景點價格 (JPY) | 文字輸入 | 可空白；若填價格則必須有景點名稱 |
| 必去景點官方價格 URL | 文字輸入 | 可空白 |
| 旅遊節奏 | radio | 四級節奏模式 |
| 住宿候補 | 系統產生卡片列表 | 由目的地與住宿預算觸發 |

### 5.2 移除的欄位

以下欄位不再要求手動輸入：

- `住宿名稱`
- `住宿總價 (JPY)`
- `住宿官方或訂房來源 URL`

取而代之的是「住宿候補選擇」與「選定後再補正式價格」。

### 5.3 範圍型欄位控制規則

所有範圍型欄位必須採用「滑桿 + 數值輸入同步」設計，使用者可以用任一方式修改值，兩者共享同一份 state。

第一版適用欄位：

- `旅遊天數`：1 至 10
- `總預算 (NTD)`：1,000 至 300,000
- `住宿預算 (NTD)`：0 至 150,000

驗證原則：

- 手動輸入不可突破欄位上限或下限。
- 系統應顯示錯誤並拒絕超界值，不可默默自動修正或截斷成合法值。
- 滑桿與數值輸入必須反映相同數值，不能各自維持獨立 state。

## 6. 右側地圖行為

右側地圖有四種狀態：

### 6.1 初始狀態

- 尚未輸入目的地時，地圖顯示預設視角。
- 不顯示住宿候補或 itinerary route。

### 6.2 城市預覽狀態

- 使用者輸入 `目的地` 後，地圖應跳到該城市。
- 這個動作不必等待 `開始規劃`。
- 若城市查詢失敗，地圖維持原狀並在左側顯示可讀錯誤。

### 6.3 住宿候補狀態

- 使用者輸入 `目的地 + 住宿預算(NTD)` 後，系統查出 3 個住宿候補。
- 地圖顯示 3 個候補 marker。
- 點選任一候補時：
  - 地圖中心跳到該住宿位置。
  - 該 marker 高亮。
  - 左側候補卡片同步顯示已選中狀態。

### 6.4 行程結果狀態

- 使用者完成住宿選擇並啟動 itinerary workflow 後，地圖切換為既有的 route map。
- 這個狀態沿用目前已驗證行程的 marker 與 polyline 呈現邏輯。

## 7. 住宿候補流程

### 7.1 觸發條件

住宿候補查詢需要下列條件：

- `目的地` 非空白
- `住宿預算(NTD)` 已設定且位於合法範圍內

符合條件後，系統立即查詢 3 個住宿候補；不需等待使用者把整張表單填完。

### 7.2 候補來源

第一版候補使用 Google Places 作為地點搜尋與地圖定位來源。這裡只把住宿搜尋當成候補推薦來源，不把 Places 包裝成房價 provider。

### 7.3 候補卡片內容

每個候補至少顯示：

- 住宿名稱
- place ID 或內部候補 ID
- 地圖定位狀態
- `符合預算傾向` 或 `價格待確認`

第一版不顯示精確房價，因為現有 provider 不保證可用。

### 7.4 選定住宿後的行為

當使用者選定一間住宿：

- 將該住宿寫入 session state
- 地圖跳轉並高亮該住宿
- 將該住宿轉成 `TripSpec.hotel`
- 解鎖 `開始規劃` 按鈕

也就是說，正式 itinerary workflow 仍然需要一間已選定住宿，但這間住宿改由候補選擇取得，不再靠使用者手打飯店名稱。

## 8. 預算語意調整

### 8.1 總預算

`總預算(NTD)` 是正式 budget gate 的總上限，行為不變。

數值邊界：

- 最小 `1,000`
- 最大 `300,000`

### 8.2 住宿預算

`住宿預算(NTD)` 僅作為住宿候補篩選與推薦依據，不是已驗證住宿費。

這表示：

- 住宿候補可用預算作排序或提示。
- 選定住宿後，若要把住宿費納入正式 budget verification，仍需使用者補正式來源價格。
- 在未補正式價格前，住宿相關費用可標記為 `MISSING_PRICE` 或維持未納入。

數值邊界：

- 最小 `0`
- 最大 `150,000`

### 8.3 幣別邊界

UI 第一層使用 `NTD`，但系統內部仍允許後續價格紀錄保存原始幣別。若使用者後續補住宿官方價格，實作可接受：

- 直接以 `NTD` 輸入，保存為 `USER_CONFIRMED_OFFICIAL_SOURCE`
- 或後續再擴充接受其他原始幣別並換算

本次 UI 改版不要求立即支援住宿價格多幣別輸入，只要求前置住宿預算改用 `NTD`。

## 9. TripSpec 與資料流調整

目前 `_build_trip_spec(...)` 直接使用 `hotel_name` 進行 Grounding。新版需改成由「住宿候補選擇結果」提供住宿資料。

### 9.1 新資料流

1. 使用者輸入目的地、旅遊天數、總預算與住宿預算。
2. UI 查出住宿候補並保存於 session state。
3. 使用者選定一間住宿。
4. `selected_hotel` 寫入 session state。
5. `_build_trip_spec(...)` 從 `selected_hotel` 建立 `TripSpec.hotel`。
6. itinerary workflow 以該住宿為起終點繼續執行。

### 9.2 輸入驗證新規則

必填：

- `目的地`
- `旅遊天數`
- `總預算(NTD)`
- `住宿預算(NTD)`
- `已選住宿候補`

可空白：

- 興趣
- 必去景點
- 必去景點價格
- 必去景點官方價格 URL

規則補充：

- `旅遊天數` 必須在 1 至 10 之間。
- `總預算(NTD)` 必須在 1,000 至 300,000 之間。
- `住宿預算(NTD)` 必須在 0 至 150,000 之間。
- 若填寫必去景點價格，必須先填必去景點名稱。
- 若尚未選定住宿候補，不得進入 itinerary workflow。
- 空白欄位不等於 provider 驗證通過，只表示尚未指定。

## 10. 錯誤處理

### 10.1 目的地錯誤

- 若目的地無法查到對應城市，顯示可讀錯誤：
  - `目的地「橫濱xxx」無法定位，請改用更完整或正式名稱。`
- 地圖不進入候補狀態。

### 10.2 住宿候補查詢失敗

- 若 Places 沒有回傳住宿候補，顯示：
  - `目前找不到符合條件的住宿候補，請調整目的地名稱或住宿預算。`
- 不產生 itinerary workflow。

### 10.3 使用者未選住宿

- 若使用者尚未選住宿就按 `開始規劃`，顯示：
  - `請先從住宿候補中選擇一間住宿。`

### 10.4 數值超界

- 若使用者在數值輸入框輸入超出邊界的值，顯示對應錯誤：
  - `旅遊天數必須介於 1 到 10 天。`
  - `總預算必須介於 1,000 到 300,000 NTD。`
  - `住宿預算必須介於 0 到 150,000 NTD。`
- 系統不得靜默改寫成最近合法值。

### 10.5 Provider 與 UI 錯誤分層

- 原始 HTTP 錯誤不直接顯示給使用者。
- Places 或地圖定位失敗必須轉譯為表單層錯誤訊息。
- 錯誤訊息需明確指出是目的地、住宿候補或景點名稱出錯。

## 11. 測試策略

這次變更至少需要補下列測試：

### 11.1 UI 狀態測試

- 滑桿與數值輸入能雙向同步。
- 數值輸入超界時，顯示錯誤且不更新有效 state。
- 輸入目的地後，城市定位狀態更新。
- 輸入目的地與住宿預算後，觸發住宿候補查詢。
- 未選住宿時，`開始規劃` 不可用或會顯示錯誤。
- 點選住宿候補後，session state 寫入 `selected_hotel`。

### 11.2 資料流測試

- `_build_trip_spec(...)` 改由 `selected_hotel` 建立住宿資料。
- 興趣與必去景點可空白。
- 必去景點價格與名稱的相依規則仍有效。

### 11.3 地圖元件測試

- 城市模式與住宿候補模式能產出正確的 marker 資料。
- 點選候補後，高亮狀態能反映在地圖輸出資料。

### 11.4 既有 workflow 回歸測試

- 選定住宿後，既有 itinerary workflow、pace gate、budget gate 不應退化。

## 12. 實作拆分建議

建議拆成四個獨立任務：

1. **表單欄位與左右布局改造**
   - 左右分欄
   - `旅遊天數`、`總預算`、`住宿預算` 改用滑桿 + 數值輸入雙控件

2. **住宿候補搜尋與 session state**
   - 即時觸發查詢
   - 候補列表渲染
   - 已選住宿狀態管理

3. **右側地圖多狀態呈現**
   - 城市預覽
   - 候補 markers
   - 候補點選後跳轉與高亮

4. **TripSpec 建立入口調整**
   - 移除 `hotel_name` 手動輸入依賴
   - 接入 `selected_hotel`
   - 保持既有 workflow 相容

## 13. 設計結論

本次改版採用「左表單、右地圖、即時住宿候補」方案，核心不是重寫 itinerary workflow，而是把住宿選擇提前成為正式規劃前的互動步驟。這樣能更早讓地圖參與、提升展示效果，並把住宿從手動輸入改為更符合產品體驗的推薦選擇流程。

這個設計同時維持既有系統的兩個重要原則：

- UI 層可以讓欄位保持彈性，但不能把空白資料誤當成已驗證事實。
- 住宿候補可以先推薦，但在沒有正式價格來源前，不應被包裝成已驗證精確費用。
